# Taken 2026-09-22 while a game was being played, after the pacing fix in b98de26, with the
# founder reporting both sticks "as good as the official control". This is the reference: if the
# pad ever feels worse than this, run tools/linkbench/linkbench.sh and compare.
#
# What each number means when it disagrees with this file:
#
#   interval other than 15.00 ms, or no line at all
#       The link stayed at the 30 ms every connection opens at. About half the sessions on this
#       day did. The pacing floor is then twice too fast and the counters below will say so.
#
#   refusals, dropped, congestion, link lost — anything above zero
#       The pad is handing the radio more than it can send. That was the whole fault this day was
#       spent finding. Zero is not "low", it is the healthy value.
#
#   more than two gamepads held by the host
#       A synthetic shim per real pad is normal; duplicates mean gamecontrollerd is accumulating
#       them, which is what wedges it and hangs games at launch. sudo killall gamecontrollerd.
#
#   gamecontrollerd not in state Ss
#       State U is the wedge. Same remedy, and save your work first: that kill has crashed
#       loginwindow on this machine.
#
#   Wi-Fi on a 2.4 GHz channel
#       This reading was taken on 5 GHz, which keeps the Mac's own Wi-Fi out of Bluetooth's band.
#       A 2.4 GHz channel here is a confound, not a fault.
#
# The disconnect count is cumulative over whatever macpair.log holds and is not comparable
# between runs. Look at whether it grows *during* a session instead.
